# Yuki 系统说明

Yuki 是一个贴在屏幕上的共读伙伴。它陪人读已经看过的 Galgame 台词或小说段落：聊感受、对情节、分清人物说辞和叙述，并在问到典故时解释。它不检索攻略，不操作游戏，也不把还没读到的内容当成已知剧情。

这份说明对应仓库里的当前源码。模型、密钥、聊天记录和剧情数据库不在仓库中。改动与验证记在 `docs/WORKLOG.md`，产品化顺序与尚未验证的目标见 `docs/PRODUCT_ROADMAP.md`。

## 界面主题

首次使用默认选择像素复古。`theme.ts`在本机`localStorage`的`yuki.theme`中记住主题，已有有效选择继续保留，未知值回退到像素。五套主题通过CSS覆盖界面外观，角色模型、阅读范围和接口配置不随主题改变。Fusion Pixel字体子集从本机资源加载，不请求外部字体服务；字体与完整OFL许可一同发布。

内置Qt浏览器使用实际布局探测启用flex间距回退；像素按钮避免旧浏览器不支持的复杂`:not()`选择器，聚焦样式提供`color-mix`回退。霓虹卡片的背景与正文同时切换，避免浅底浅字。`scripts/verify_themes.cjs`使用隔离自编故事检查默认主题、五主题切换与重启、字体加载、两档小窗和夜间卡片可读性，不调用外部接口。

## 运行与首次使用

资源由 `yuki_paths.resource_root()` 定位，个人资料由 `data_root()` 定位。源码版默认沿用项目目录；打包版使用 `%LOCALAPPDATA%/YukiAI`；`YUKI_DATA_DIR` 或启动参数 `--data-dir` 可指定独立目录。配置、数据库、聊天、取词工具及窗口缓存使用个人目录，静态界面使用资源目录。源码启动不再依赖某个开发者的Python路径。

打包桌面程序显式设置随包Qt组件位置，保留打包运行钩子的插件路径；Windows非ASCII资源目录通过系统短名称交给Qt5的资源加载器，目录本身和个人资料不搬移。系统未提供可用兼容名称时返回可读的启动提示。构建附带相对路径 `qt.conf`，参考 [Qt路径配置说明](https://doc.qt.io/qt-6/qt-conf.html)。

Qt5的ICU初始化还会读取模块自身的位置，因此非ASCII可执行路径在启动桌面前会以同一文件的兼容名称启动独立实例，并保留全部参数和资料位置；原进程等待其退出。使用 [PyInstaller独立实例环境重置](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html#using-sys-executable-to-spawn-subprocesses-that-outlive-the-application-process-implementing-application-restart)，并设置一次启动标记防止循环。预览服务和只读检查无需重启。

普通构建按需加载本地Live2D运行库和模型；不可用时使用原创2D纸签。模型代码改为延迟加载。Alpha构建不复制public目录，也不输出Live2D代码块，所以克隆仓库或使用免安装测试包无需取得私人角色素材。纸签的透明区域仍不触发操作栏，人物原有表情、比例及悬停行为保留。

首次无接口、无共读时打开引导，也可从“···”重开。示例明确展示三句自编原文，玩家确认读完后通过现有共读/导入接口保存到独立共读。“粘贴我的剧情”创建新的游戏共读；“准备问题”只填写草稿。配置保存、原文整理不调用LLM，连接测试与发送分别由玩家触发。取词页提供手动粘贴退路，尚无OCR或自动剪贴板监听。

## 1. 它解决什么问题

普通搜索和直接问通用模型，用的是整部作品的介绍、攻略和训练记忆。Yuki 用的是你这条阅读进度里已经确认读过的原文。

因此它适合这些问题：

- 刚才这一段在说什么。
- 这句话里的典故指什么。
- 到目前为止，这个人说过什么，叙述里又写了什么。
- 我回到前面的进度了，按现在这段重新聊。

它不适合这些问题：

- 真结局怎么达成，选哪句，后面谁会死。
- 还没收录的章节里发生了什么。

## 2. 两种阅读

建立共读时选择一种。选择写在 `runs.mode`，默认 `galgame`。

| | Galgame | 小说 |
| --- | --- | --- |
| 进度单位 | 路线、书签、分支、回档 | 章节和已读段落。界面仍保留书签，用来停在某一句 |
| 如何认人 | `美咲：台词`、`【美咲】台词` | 同上，另外认识 `孔乙己说道，“……”` |
| 如何分段 | 选项、时间地点转换，或满 40 句 | 再加 `第一章`、`第X回` 这类标题 |
| 提问语气 | 不谈选项后果 | 不谈路线、选项和攻略，也不许用书名补后文 |

`他/她/我/你` 开头的“说道”不会被当成角色名。

## 3. 一次提问怎么发生

界面把问题和当前 `epoch` 发给本机 `POST /api/chat`。服务只在本机 `127.0.0.1` 上。

1. 用 `epoch` 确认阅读进度没有在提问期间被换掉。
2. 若当前没有共读，就走普通聊天：最近对话加角色设定。
3. 若正在共读，只从当前路线、当前位置以前的原文里取材。
4. 材料打成一份 JSON，连同模式对应的系统提示，发给设置里的 OpenAI 兼容接口。
5. 回复必须是一个 JSON 对象，含 `text`、`emotion`、`answer_type`、`evidence_ids`。
6. 引用编号必须来自这次打开的句子。分析类回答不能没有编号。
7. 若回复里出现材料中没有的结局、真实身份或选项后果，相关句子会被删掉；整句都站不住时，改成不确定并清空依据。
8. 通过之后才写入本地记录。界面上的「依据」打开的是本机保存的全文，不是送给模型的截断文本。

模型若没按 JSON 返回，会先从文本里抽出 `{...}`。仍然失败就再请求一次。两次都不行，界面得到一条不含上游正文的错误。

敏感措辞检查的语料只取本次打开的 `events.text` 与说话者，不再加入问题、作品名、讨论、手记、目录、人物索引或未发送的 `raw_text`。这防止把玩家提问及旧推断当成剧情证明，仍不具备逐条语义支持验证；原文中出现相同关键词，也不证明回复里的完整推断成立。

普通聊天和共读讨论是分开的。共读不会把另一条路线的聊天带进来。

## 4. 记忆如何节省上下文

原文一直完整留在本机 SQLite。送给模型的只有一小部分。

分段规则在 `scripts/yuki_story.py`：

- 一场最多 40 句。选项、章节标题，或旁白开头的“第二天 / 与此同时 / 【场景】”会另起一段。
- 先打开问题对上的那一段。若它不是当前结尾，当前进度只再留最后 4 句，用来标明人读到哪里。
- 正在读的短段（不超过 12 句）整段打开。更长时打开结尾 8 句、开头的旁白，以及问题点名的那一句和它前后各 2 句。
- 更早的段落最多再打开 2 段，而且必须和问题对得上。只因为共享一个两字片段而分数差很多的段落不会打开。
- 送给模型的材料里写明确认进度，以及这一问问的是第几句。问得更早只表示在回顾，不把进度改到那里。
- 问题会切成 2、3、4 字。较长的词权重大，用来压过“的灯”这类常见两字。
- 单句送给模型时大约不超过 160 字，并尽量留住问题里的词。全文仍在数据库里。
- 打开的原文预算大约 2400 字。放不下时优先留下点名的句子和当前结尾。
- 没打开的段落只留目录：范围、在场的人、开头一句短摘录。目录最多 8 条。
- 最近讨论只带 6 句，每句大约 180 字。
- 人物索引里，已经打开的句子只留编号，避免同一句台词送两次。没打开的说辞才附上短文本，而且不能当作引用编号。

人物卡把两类分开：

- `claims`：这个人自己说的。
- `witnessed`：叙述里提到这个人。

说辞不会被改写成事实。

## 5. 进度、分支和回档

当前可用原文 = 当前作品的这一次阅读 + 当前分支祖先链上、阅读位置以前的已确认事件。

不能用“这个人历史上读过的全部句子”。回到书签之后，书签后面的句子，包括另一条分支里的句子，都不会进入提问、目录、人物卡或讨论。

阅读位置要经过连续核对，不能凭一句重复台词就改：

- 取到一句和较早原文相同、并且足够长的台词时，先记住，不写入。下一句若正好是它后面的那句，才判定回到了旧进度，暂停记录，并请你回书签。下一句对不上，就只把后一句当新台词。
- 一次粘贴若从某一句起连续两句都和已读原文相同，会拒绝写成新进度。
- 连续两问都落在比确认进度早至少 12 句的同一处，剧情记录和回复下方都会写明“最近两问都在看第 N 句附近”，但进度数字不动。回顾不是读档。小说回复不会把这段叫成“路线”。

这些动作会增加 `epoch`，并取消还没回来的回复和朗读：换一篇共读、回档、改阅读位置、切换分支、新开一段讨论。向前继续收录通常不取消正在进行的、针对旧进度的合理回复；若回复回来时进度已经对不上，它不会被保存。

共读手记使用独立的 `runs.note_generation`：修改手记会取消旧回复与朗读，取词的阅读 `epoch` 不变，因此继续记录。模型快照同时核对手记版本；手记更新前的讨论保留在记录中，但不再作为当前模型对话上下文或最新气泡。分支还保存 `note_cutoff` / `turn_cutoff`，子路线只能继承分支建立前的父路线手记和讨论，包含同一阅读位置的版本边界。

在回退位置继续收录新文本时，会另存一条分支，旧分支保留。

小说的默认分支名叫「正文」。Galgame 的默认分支名叫「共同线」。

## 6. 取词

Galgame 可以用本机的 Textractor 取当前窗口里的新台词。流程在 `scripts/yuki_capture.py`。

- 先选游戏进程，再选和画面正文一致的来源。菜单、单独跳出的姓名不要选进正文。整行就是「保存」「读取」「F5」这类界面文字时，预览里还能看到，但不会写入正文。短的对白，例如「知道了」，仍会保留。
- 开始记录之后才写入。预览里的旧句不会补录。
- 大约 1.5 秒内的连续重复会丢掉。逐字增长的同一句会合成一句。不同场景的正常重复会保留。
- 取词本身不调用模型，也不合成语音。
- 回档、换共读、换路线、来源过多、单条过长或取词过快，都会暂停写入。
- 它不能发现游戏自己已经读档。读档前要先暂停，回到对应书签，再重新开始记录。

小说目前以手动收录为主。每次最多 200 行、每行 2000 字。

## 7. 界面和桌面窗口

`app/src/` 是小窗页面。`scripts/yuki_window.py` 用本机 Qt 打开透明窗口，默认 320×460，最小 280×380。启动后先只显示一个可拖动的 Yuki 按钮；点击或按 Ctrl+Alt+Y 打开或收起小窗。收起时本机服务、阅读记录和取词继续运行。右键按钮可以退出。

页面上能做的事：

- 拖动角色附近的操作栏移动窗口。平时操作栏隐藏。
- 一条浅色气泡。短回复随文字变窄，长回复先显示三行。
- 点「聊聊」才输入。回想、新聊和收起在「···」里。
- 设置里填写聊天和语音。密钥只留在本机，接口不把密钥送回浏览器。
- 语音默认关闭。可以试听，或让它朗读当前中文回复。
- 「剧情记录」里收录原文、书签、路线，以及「目前记得」。
- 共读回复若依据不足，气泡下方会说明，回想里标「没把握」。

没有麦克风、摄像头、读屏或代替玩家操作游戏的功能。

## 8. 本机文件

“剧情记录 → 记忆管理”能查看占用、管理旧讨论和普通聊天、备份与恢复全部记忆。备份为版本化的逻辑快照：在同一个数据库读事务内读取所有共读表，兼容尚在 WAL 中的已提交内容；普通聊天只提取消息和已知元数据字段。备份不读取设置和模型。恢复前在隔离数据库校验结构、外键、分支祖先链、进度和引用范围，恢复时为共读、分支、原文、书签、讨论分配新编号，重写引用，保留现有资料。异常时回滚共读写入并清理本轮创建的聊天副本。

清空讨论会删除所选共读的全部 `story_turns`，包含旧 `chat_generation` 和所有路线；原文、明确留下的手记和书签保留，手记的讨论来源外键置空。删除共读会在单个事务中删除其所有从属记录及回顾缓存，只在作品没有其他共读时移除作品条目。记忆管理中影响阅读的清理/恢复会递增 `epoch`，取消旧回复/语音并暂停取词；界面同步移除缓存引用。普通聊天也可以找回或删除。

清理先生成五分钟有效、一次使用的预览令牌。确认时核对阅读 `epoch` 和该次共读的版本摘要，防止刚收录的台词、新讨论或手记被旧预览删除。恢复采用独立副本，不覆盖原记录。备份独立保留并可单独删除；没有自动保留期限或回收站。“整理空间”执行检查点和 VACUUM，只回收空闲页，不保证磁盘安全擦除。当前派生场景和人物卡仍从有效原文重算，未引入自动生成的长期语义摘要缓存。

`reading_notes` 保存按阅读位置和分支追加的手记版本，分为疑问、猜测、感受；状态仅代表玩家是否想继续讨论。查询取祖先链与位置范围内每条手记的最新可见版本，父分支还受版本截止编号约束。删除一条手记会删除所有版本。模型最多收到四条相关手记，每条约200字，标为 `player_notes`，不能把手记编号当成剧情引用。相关手记关联的原文可以参与打开剧情块，仍受原有总长度预算限制。

`reading_recaps` 每条路线只缓存最近一次回顾：原文摘录和当前讨论最近三个话题。指纹包含进度、原文编号、讨论、阅读记忆版本；回档后不复用较晚进度的缓存。损坏缓存可以重建。回顾不额外调用模型。备份v3保存手记及人物纠正版本，恢复时重写讨论来源、原文、纠正锚点和分支截止编号，回顾缓存不备份；兼容v1、v2并补齐新字段。旧路线缺少可靠的建立时版本边界，升级时使用保守截止值，保留数据库原记录。

`character_corrections` 保存玩家核对的称呼和单句指代，包含逻辑编号、版本编号、路线、保存位置、原文锚点和依据。称呼按当前路线可见版本合并派生人物卡，保留原始台词的说话者。指代按当前原文位置生效；问题明确指定唯一的“第N句”时，也可以调用那个位置的历史纠正。复数“她们/他们”和“其他”不套用单数纠正。目标及称呼必须在当前路线已读原文中出现，禁止多层或循环别名。它不自动验证人物身份，也不构成剧情证明。

保存前预览原文，保存时重做校验，核对阅读位置、`epoch`、阅读记忆版本和被编辑版本。保存和删除递增 `note_generation`，取消旧回复/朗读且拦截迟到响应，取词继续。分支记录 `character_cutoff`，按建立时版本继承；删除移除同一逻辑纠正的全部版本，保留原文。清空讨论保留这些明确纠正，删除共读一并清理。模型最多收到六条相关对应，明确标为玩家核对，引用仍只允许本次实际打开的原文编号。

启动：双击 `start_yuki.cmd`，或用 myenv 的 Python 运行 `start_yuki.py`。默认端口 12393。`--mode preview` 不调用外部接口。`--headless` 只开本机页面。

前端改动后要在 `app/` 里执行 `npm run build`。服务读取的是 `app/dist`。

聊天接口是 OpenAI 兼容的 `/chat/completions`。当前本机示例是 Command Code 的 `https://api.commandcode.ai/provider/v1`，模型名形如 `deepseek/deepseek-v4.1-flash`。DeepSeek 请求会关掉额外的思考字段，减少不按 JSON 返回的情况。语音可以是 Fish Audio 或另一路 OpenAI 兼容合成，默认关闭。

## 9. 主要接口

全部只接受本机来源。

- `GET /api/status`、`GET/POST /api/settings`、测试聊天和测试语音。
- `POST /api/chat`、`POST /api/speech`。
- `GET /api/story`，以及建立、切换、收录、书签、回档、进度、分支、新讨论。
- `GET /api/story/continuity`（可用 `before_note` 分页），`POST /api/story/notes`、`notes/delete`：阅读回顾与手记；只接受当前已读范围的原文关联，删除要求明确确认。
- `GET /api/story/timeline`：当前范围内的卡片；`before`向前分页，每页最多24张；`kind`、`speaker`、`q`按类型、原文说话者及全文关键词筛选。响应携带epoch、路线、位置和手记修订号，前端丢弃过期响应。
- `GET/POST /api/capture/...`：进程、连接、选来源、开始、暂停、断开、手动 Hook 码。
- `GET /api/story/characters`，`POST /api/story/characters/preview`、`save`、`delete`：人物纠正列表、只读预览、明确确认后保存或删除全部版本。
- `GET /api/memory`，`POST /api/memory/backup`、`plan`、`confirm`、`compact`、`history/open`：占用、备份、预览/确认、空间整理和找回普通聊天。接口只处理本机生成的备份编号，不接受文件路径。

收录接口要求明确勾选“这些内容我已经读过”。

## 11. 已知边界

- 热门作品仍可能被模型用另一种说法讲出后文。现在会拦截“真结局”“真实身份是某某”“选 A 会”这类明确说法，挡不住换一种说法。
- 没有玩家纠正时，最近一段里有好几个人说话，“她”或“他”只能暂定成最后开口的那一位，回答要先说明指的是谁。只有一个人时，会按这个人打开较早的原文。小说如果几乎没有对白，就用已读文字里反复出现、而且明显多于其他词的那个人名；分不出先后时不当成确定指代。玩家可在人物与称呼中明确纠正，系统仍不自动推断隐藏身份或关系。
- 取词不能自动发现游戏读档，也不能保证每一款游戏的 Hook 都正确。
- 「目前记得」展示最近四段，以及最近说过话的十二个人。更早的内容要提问才会打开。
- 整理目录和人物索引不调用模型，所以它不会自己写出一段文学性的长摘要。
- 脉络卡片也是本机派生视图：按现有场景边界切开，每张最多6句，单列章节与选项，显示最多3条摘录并可打开完整原句；不把规则分段称为剧情理解或因果分析。卡片以首条原文ID标识，部分已读时重新截断。手记作为另一类卡片，位置代表写下或修改时读到的句子；修改沿用版本和分支截止，删除会清除所有版本。没有独立卡片表或冗余摘要缓存，备份恢复后从原文和手记重建；删除共读即可清除其全部卡片。卡片编辑附带阅读位置及手记修订号，避免自动取词推进或另一客户端修改后继续保存旧编辑器。
- 确定性测试能保证另一条路线的原文没有送进本次请求。它不能证明模型的训练记忆绝不泄漏。
